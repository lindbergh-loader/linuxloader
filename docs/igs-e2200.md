# IGS E2200 dumps

How the `e2200_*.chd` disks became game directories, and where the work
stopped: each executable is out and decrypted. Five of them are still
wrapped in a Sentinel HASP envelope; Fish Hunter SKL 2 is not, and only
calls the HASP API. The HASP and runtime-recovery investigation is documented in
[igs-e2200-hasp-codex.md](igs-e2200-hasp-codex.md).

```sh
tools/igs-e2200-extract.py games/e2200_soulofgun_m102cn.chd "games/Soul of Gun" games/work
```

| Disk | Directory | Executable (in `game/`) | Kernel |
| --- | --- | --- | --- |
| e2200_soulofgun_m102cn | Soul of Gun | SoulOfGun | May 21 2012 |
| e2200_fishhunterskl2_m801cn | Fish Hunter SKL 2 | FHSKLv2-8p | Apr 15 2012 |
| e2200_fullattack_m802my | Full Attack | OceanKing | Oct 30 2012 ("OceanKing") |
| e2200_oceanking_m817cn | Ocean King | OceanKing | the same |
| e2200_poseidon_m806cn | Poseidon | OceanKing | the same |
| e2200_westtrip_md108cn | West Trip | WestTrip | May 20 2012 |
| e2200_percussionmaster3 | Percussion Master 3 Original | exe/pm3 (decoded payload) | Dec 7 2011 |

West Trip's bundled licensing daemon is now recovered for analysis;
its game envelope remains unresolved. See [the follow-up](igs-e2200-west-trip-envelope.md).

PM3 uses a different layout and extraction path; see
[the original PM3 recovery](igs-e2200-pm3-original.md). The general
IGS_SHFS extractor below applies to the earlier six dumps.

Full Attack, Ocean King and Poseidon share one kernel, root layout and
loader. Only their data and executable differ. Four of the five 2026-11-24
dumps (all except Full Attack) are shorter than their partition tables say.
Every squashfs still ends well before the cutoff.

Per kernel, everything the tool needs is read from the kernel and the root
rather than hardcoded:

- the boot names: the strings around `__KERNEL__`, in the same order in every
  kernel;
- postcat's two raw reads: the immediates in its code;
- GECA's builder arguments: its `main`'s moves, followed through objdump.

The tool needs `chdman`, `unsquashfs`, and `gcc -m32` with 32-bit zlib. Output:

- `game/`: the cabinet's `/SOG`. It holds the data, `SoulOfGun`, and `lib/`
  with the libraries a desktop lacks (SDL 1.2 + SDL_mixer, GLU, Xxf86vm,
  ncurses 5, pci 3).
- `boot/vmlinux`: the cabinet's kernel.
- `boot/rootfs/`: the decrypted root.

The cabinet runs the game from `/SOG` as `./SoulOfGun` with no arguments,
after `aksusbd`, `winehasp` and `hasplmd -s` (see `boot/rootfs/etc/X11/IGS`).

## E2100 disks

`tools/igs-e2200-extract.py` also handles the `e2100_*.chd` disks (same
partition roles, root in igs_rofs v2 decrypted by the kernel's own driver).
Three boot schemes:

| Disk | Directory | Executable (in `game/`) | How the cabinet gets it |
| --- | --- | --- | --- |
| e2100_scratch_m101cn | Scratch | SWIN | kernel runs `/bin/unrar /Scratch/swin /Scratch.bin/swin Hello-ScratchWin` |
| e2100_crazyshoot_m100cn | Crazy Shoot | CrazyShoot | E2200 GECA build (postkick `/usr/bin/robn`, postcat `/usr/sbin/pegan`, no `tmpfs` string), IGS_SHFS hda3 |
| e2100_demonhunter_m202cn | Demon Hunter | zombie | plain on the root (`/Zombie.bin/zombie`); M100CN and A38 versions not kept |
| e2100_heroofrobots_m100fa | Hero of Robots | exe/child_linux | plain (`/Robots.bin/child_linux`); Ogre libs in `data/so` |
| e2100_oceanparty_md105cn | Ocean Party | OceanParty | plain |
| e2100_demonhunter_m102cn_a38 | (not extracted) | | Ocean King 2's A38 scheme: GRUB 0.94, 8 MiB encrypted kernel blob at 1 MiB, dm-crypt hda2 keyed by the A38 board |

`unrar` is not RAR: it streams the file through the FPGA (`/dev/pccard0`,
ioctl 0xc0106610, key set by 0x6607/0x40106606/0x6608/0x80106605), the same
cipher as postkick, so the keyless `fpga_decrypt` (mask = most common block)
decrypts it.

hda3 (plain squashfs, or IGS_SHFS for Crazy Shoot) links into a ramfs
`/<Game>.bin`; the tool fills those links from the root (decrypting unrar's
`<dst>`). The executable is the `./NAME` the root's `etc/X11/IGS` runs, after
its last `cd`. Hero of Robots' `exe/child.rom` link has no source on the root
(made at run time?).

### Running them

The `asic36.bin` beside each SDL game is not what it sends: the game reads
it, then uploads a 512 KiB firmware embedded in its ELF (the
`movl $0x80000,4(%esp); movl $ADDR,(%esp)` before its LoaderAdv_iLoadData):
Ocean Party 0x08257c00, Demon Hunter 0x08246be0, Scratch 0x0817e900. Each
decrypts with `tools/igs036-firmware.py --body` (references: Fish Hunter
SKL 2's, Speed Driver 4's ROMs) to `game/roms/<name>_eprom.bin`, its hash
matched.

Ocean Party (`scripts/linux/runop.sh`, igsGames.c) runs on the A36 path:

- the internal ROM's services table at SRAM 0x0200f000 (0x1001cb30 calls
  it; empty, service 1 jumps to 0: a reboot loop);
- the assets' cipher mask `5bc95914 4ae93411 30be7837 efec7893` (the
  permuted most common block; files start `ACT_ZL3D`);
- DIP switches at 0x03900000, active low (switch 1 the game mode; reading
  it ON gives the "mode changed" warning screen);
- timers on a 65 MHz master clock (its baud rates, 0x10014530), and its
  time kept to the wall clock (its main loop polls, no idle loop);
- the RS485 control board on USART0 (igsStm32.c `opByte`): the firmware
  sends a command, its data (0xc2: 7 bytes, the polls: 50, the seats'
  LEDs) and their sum and a 0; the board answers the polls with 0xc1, 25
  input bytes (active high) and their sum.

Its 200 input bits: 0 the test switch, seat n's 19 buttons from
8 + 24 n (1P bottom left, 2P bottom right, 3P right, 4P top right, 5P top
left, 6P left): the 8 fish, shark, no-shell x2, shell x2, bet switch, cancel
bet, repeat bet, coin out, hide score, key in, key out, troubleshoot (the key
test shows them). Credits come from key in. The seats' credits and bets are
on the cabinet's LEDs only; the loader draws them by each seat, from the
board's external SRAM (credits 0x500000c8 + 4 n, bets 0x50003ef4 + 0xa0 n:
the total, then each target).

Demon Hunter (M202CN, `scripts/linux/rundemon.sh`) the same way, with:
the services table at 0x0200f000 too, its own assets' mask (`42441fc3
db08f347 e125b1e6 d1f1c326`, sounds included), Fish Hunter SKL 2's sound
loader bug (its fix: soundLoad 0x080630f0), a 1280x720 frame although it asks
for the screen's size (a36AsksScreen), and Fish Hunter SKL 2's control board
on USART1 with 10 input bytes (firmware 0x1000d6e4; active low, seat n byte n,
bits 0/1 up/down, 2/3 turn, 4 button, 5 fire, 6 coin).

Scratch (`scripts/linux/runscratch.sh`): its Flash pictures (`*.swf.ifs`)
and Ogg sounds are plain; its picture shader's GL ES `precision lowp float;`
(desktop GLSL 1.10 rejects it: a white screen) blanked; Demon Hunter's
control board on USART1 (fish 6: seat n byte n, 0 bottom left, 1 bottom
right, 2 top left, 3 top right; up/down the ticket's price, left/right the
ticket, 4 manual or quick scratch, 5 take the ticket, 6 coin; no free play);
its lamp board on the PC's /dev/ttyS0, written only (on /dev/zero); 1920x1080.
GLEW's old libXi left out of lib/ (the loader's glut needs XI2).

Hero of Robots (M100FA, `scripts/linux/runrobots.sh`, `child_linux`, an
Ogre game run from `game/exe` with `game/data/so` on its library path; its
`rw_data` from hda4): the firmware embedded at the loader's iLoadDataPointer
(the 5th a36Loader entry starts the board at install), 16 MiB of RAM and of
external SRAM, the services table at 0x0200f000, timers on the 20 MHz
default (the firmware's watchdog, 0x02000648, gives the PC 10000 ticks to
send its first scene's command 2; on a 65 MHz clock it ran out during the
loading screen and the board halted at 0x100044b4).

- Its I/O board on USART1 (fish 7, igsStm32.c `robotsByte`): 13-byte
  frames from the firmware (0x29, the game's 12-byte packet), 12-byte
  answers (0x2a, the keys in bytes 1-3, active high, a sum). The game's key
  word (Game::iIgs036_RecvCmdPrcess, Credit::_vProcess): bits 0-2 player
  1's red button (confirm, start), blue button (skip) and lever (select),
  4-6 player 2's, 9 down, 10 up, 11 test, 12 service, 13 coin.
- Its card reader (CASTLES EZ100PU, libcas): one reader, no card in it
  (igsCard.c); the operator's prepaid-plays chip there with credit.
- Its card dispenser (COM2: `01 37` status 23, `01 38` sensor 30/31, `01
  39` version, `01 42` a card out: 50) and QR scanner (COM1: ESC 0/1, each
  command ACKed; a card: its 17 digits and CR LF), each a socketpair
  (rs232Initialize, chosen by its caller).
- The QR codes: the board decodes them (command 0x0e, 0x10005214) to the
  card's number in `media/localization/Card/QRCardRes.csv` (`0102VVKNN`:
  series VV, kind K 1 robot / 2 power / 3 skill, number NN): 16 of the 17
  digits (the 9th not read), 3 bits each (the digits 9 1 8 7 6 5 0 2), the
  48 bits shuffled into 6 bytes (byte 0 a CRC of bytes 1-5, the firmware's
  own table), bytes 1, 3 and 4 mixed with 5 and 2, 32 bits shuffled into the
  number. It runs backwards: the card binder makes any card's code.
- The card binder (igsBinder.cpp, Dear ImGui at the swap): Tab or LB on the
  insert card screen; the game's 1002 cards with a QR (series 1-12, events)
  and their pictures (`media/localization/ui/common/card/<print>_I1.dds`);
  a hand of a robot, a power card and a skill card, scanned one after
  another with Return or Start. Each card the dispenser gives is one of
  series 12 at random, shown a while, kept in the "Dispensed" tab.

Desktop keys: 5 coin, 1 or Space red (start, confirm), Z blue, X lever, F2
test, F1 service, arrows the operator's menu; pads: A red, B blue, X/Y/RB
lever, Start, Back coin.

None of the six executables is packed: glibc `_start` at the entry inside
`.text`, normal code entropy (5.9-6.4), no HASP/Sentinel/UPX markers.

## Percussion Master 3 comparison package

Percussion Master 3 is also E2200, as identified by the user. The local
`games/Percussion Master 3/` is a prepared TeknoRaven package, rather than
one of the six original CHD extractions above. It must be kept separate
from evidence about original cabinet protection.

Its `game/exe/pm3` is a 26,091,136-byte ELF32 with normal libc startup at
`0x08553150`, which calls accessible `main` at `0x085bcd20`. Full-file
searches found no `hasp_`, `HASP`, `THaspKeyPro`, or `FAFC_` markers. It
does not have the five games' envelope entry trampoline. Numerous dynamic
symbols survive, including the FPGA communication/AES wrappers and
`Igs036P2A` methods, making it useful for comparing board protocols.

The supplied `game/roms/a36rom_fpga_decrypted.bin` is 512 KiB; REA decodes
coherent ARM vectors and processor-mode/stack setup. Its configuration
declares `external_rom_encrypted: false`. This firmware was supplied with
the package, not recovered during the current investigation.

Executable SHA-256:
`429cd794e89bd7d3997325d4310a2ee026de8f95c67f97a9f7f4738b6d746e46`.
Firmware SHA-256:
`01108a2f9270ade7c9be28343725a0480ca2052cbf837339df01084ef9fee93f`.
Both hashes and the configuration match the supplied `SHA256SUMS`.

The original CHD has now been inspected: its executable was recovered
through the FPGA transform and also has normal startup without an
observed HASP envelope. It is a different build from this prepared copy.
No PM3 runtime test was performed. See
[the original-dump comparison](igs-e2200-pm3-original.md).

[REA evidence](igs-e2200-pm3-evidence.json).

## The disk

| Partition | Content |
| --- | --- |
| hda1 | ext2 behind a "Game Image v2" header: scrambled metadata, plain data blocks. Holds the kernels LILO boots. |
| hda2 | the root, igs_rofs v2, encrypted with AES |
| hda3 | IGS_SHFS, the same format as the E3000's (squashfs 4.0 behind the `d4aa2682` superblock), mounted on `/SOG` |
| hda4 | ext3, `/SOG/ScreenCutOff` (empty on this dump) |

Unlike the E3000, the SHFS root is the game directory itself: there is no
`data/` folder. Its `SoulOfGun` entry is a link to `/SOG.bin/SoulOfGun`.

**The kernel.** It is the last bzImage on hda1. Its file is not contiguous:
the ext2 indirect blocks sit between its data blocks. They are plain, so
the tool follows them (12 direct blocks, the indirect block, then the
double-indirect block). Read contiguously, the gzip fails its CRC.

The vmlinux keeps kallsyms (2.6.32 layout: addresses, num_syms, names,
markers, token table, token index). It names everything used here:
`ROFS_Decrypt_*`, `igs_rofs_*`, `FS_AES_*`, `FPGA_*`, `init_post`.

## The root (igs_rofs v2)

`init_igs_rofs_fs` copies one string, `FSV2SoulRO-OfGun`, into the three
AES-128 keys:

- single blocks: ECB;
- names: CBC with a zero IV;
- file data: CBC with a zero IV, first 0xa0 bytes only.

The AES tables are standard, but the results do not match a stock AES with
that key (no byte-order variant matched either).

Each kernel also has its own variant of the format:

- its own key string and XOR constants;
- its own inode layout: which 16-byte block and word holds each field, the
  mode at 0x74 or at 0;
- its own offset tweak (`+0x4172`, `-0x2b5e`, `+0x52e6`, `+0x8179`).

So `tools/igs-e2200/igs-rofs.c` does not reimplement the format. It runs
the kernel's own igs_rofs driver in a 32-bit process:

- the vmlinux's segments are mapped at their addresses (0xc1000000);
- the kernel services the driver calls (locks, kmalloc/vmalloc,
  iget5_locked, d_alloc_root, kmap, unlock_page, igs_rofs_read, printk)
  are patched with jumps to stand-ins, found by name in kallsyms;
- it then calls init_igs_rofs_fs, igs_rofs_fill_super, igs_rofs_readdir,
  get_igs_rofs_inode and igs_rofs_readpage as the VFS would.

Common to every kernel:

- every inode field is a separately encrypted 16-byte block;
- offsets and sizes are XORed with constants;
- each file page is a zlib stream whose header bytes were overwritten.

## The executable

Built at boot by the kernel's `init_post`:

1. Mount a ramfs on `/mnt` and run `/usr/sbin/postcat /usr/bin/bison __KERNEL__ "-no-print -SoulOfGun"`.
   postcat writes two files:
   - `/mnt/head`: 1 KiB of raw hda3 at sector 0x1d9f7d;
   - `/mnt/GECA`: 1 KiB of raw hda2 at sector 0x5048e (an ELF header,
     alone in the 0xaa55 fill past the root), followed by `/usr/bin/bison`.
     The result is a small loader.
2. The kernel runs `/mnt/GECA` (same arguments). Like Gold Captain's csh,
   it builds the encrypted executable from pieces:
   - it cuts the middle of each `/lib/libsog<n>.so`, in the order
     `14523768`: 20 KiB off the start then 2 less each time, 12 KiB off
     the end then 2 more each time;
   - it mounts a ramfs on `/SOG` and cats `head` + the pieces into
     `/SOG/SoulOfGun`.
3. Mount a tmpfs on `/SOG.bin` and run
   `/usr/sbin/postkick /SOG/SoulOfGun /SOG.bin/SoulOfGun MBSoulE22OfGunUD`.
   postkick loads the key into the FPGA (`/dev/pccard0`, ioctls
   0x6607 / 0x40106606 / 0x6608 / 0x80106605). It then decrypts the file
   in 64 KiB chunks (ioctl 0xc0106610) and deletes the source.
4. Mount hda3 on `/SOG` (shfs) and hda4 on `/SOG/ScreenCutOff`, then run
   `/sbin/init`.

The FPGA does the cipher in hardware, but it is the A36's (`igsA36.c`'s
`cipherPerm` plus a 16-byte mask) run in the other direction:
`encrypted = unpermute(plain) ^ mask`. The mask is the encryption of a
zero block, which is the file's most common 16-byte block (77,655 times):
`ba3b1c9b86e3337a47d2efae088233c2`.

The other games use the same scheme with their own names, keys and GECA
parameters:

- pieces: `/usr/lib/libshadow<n>.so`, `/etc/rc.d/rc<n>.d`,
  `/usr/lib/libmenu<n>.so`;
- different orders and skip/drop steps.

The ELF header block checks the mapping. For Soul of Gun the result is a
valid ELF:
`SoulOfGun`, 10,359,376 bytes, md5 `3dd7a9c883362a4358bd9db9c810e17d`. It
needs SDL 1.2, SDL_mixer, GL/GLU, Xxf86vm, X11, zlib, ncurses 5, pci 3 and
libstdc++.

## Runtime assets and board firmware: recovery results

Follow-up work on 2026-11-24 recovered the runtime graphics/sound transform
for all six games and verified two decrypted IGS036 board ROMs. The
[investigation handoff](igs-e2200-hasp-codex.md#current-handoff) contains
addresses, masks, firmware keys, evidence links, and remaining blockers.

| Game | Asset files validated | Board ROM |
| --- | --- | --- |
| Fish Hunter SKL 2 | 81/81 | Recovered; embedded hash matched |
| Soul of Gun | 182/182 | External `asic36.bin` found; decryption unresolved |
| Full Attack | 151/151 | No external image found |
| Ocean King | 170/170 | No external image found |
| Poseidon | 169/169 | No external image found |
| West Trip | 305/306 | Recovered; embedded hash matched |

The asset cipher is `plain = PERM(cipher XOR mask)`, using the extractor's
existing bit permutation with a different mask for each game. Those
effective masks are sufficient to decode the observed files; they are not
the original FPGA user keys or the HASP AES secrets.

[igs-e2200-assets.py](../tools/igs-e2200-assets.py) can recover the mask from
a known graphics header and validate the remaining chunk layouts. It also
recognizes plaintext assets and handles Soul of Gun's two sounds with a
second mask:

```sh
python3 tools/igs-e2200-assets.py inspect 'games/Ocean King/game' \
  --auto-mask --report /tmp/ocean-king-assets.json
```

This reads the game directory without changing it. Report paths must be
new. Use `decode INPUT OUTPUT` with the report's `--mask` to write an
individual decrypted asset; the output must also be new.
West Trip's `sound/Sound_CrazySay01.wav` appears truncated: 49,152 bytes
on disk versus 393,958 bytes declared by its decoded RIFF header. Its
inspection therefore exits nonzero while retaining the other results.

The saved board firmware artifacts are:

| Local file | Bytes | SHA-256 |
| --- | --- | --- |
| `games/Fish Hunter SKL 2/game/roms/fhskl2_eprom.bin` | 524288 | `9fb6b74a57e9214dabe02db668643de02867ecf43e08c0de0dff8498dba2c8f5` |
| `games/West Trip/game/roms/westtrip_eprom.bin` | 524288 | `d6f2ebb6879d19569a1bdc86c0384095246896acf4337fa7e2e4a1fa9eb49d78` |

Fish Hunter's upload is embedded at executable VA `0x082d4d20`, length
`0x90000`, including a 64 KiB loader header. West Trip's external
`asic36.bin` is headerless and already past the FPGA permutation stage.
[igs036-firmware.py](../tools/igs036-firmware.py) now supports those
input differences through `--body` and `--no-fpga`. Exact reproduction
commands and saved recovery parameters are in the handoff and its linked
JSON files. The two ROMs were regenerated from their retained key/mask
pairs, reproduced byte-for-byte, and passed their embedded hash checks.

Asset validation checked chunk boundaries, texture dimensions, and PCM
metadata across **1,058/1,059 files**. Independent DDS decodes succeeded for
all six games, and a Fish Hunter WAV loaded independently. Fish Hunter
also reached `main` under a bounded debugger probe after supplying the
cabinet's missing `libtinfo.so.5`. These are recovery and startup results;
no production loader descriptor, complete dongle replacement, board
emulation, or gameplay launch has been validated.

## Remaining blocker: the HASP envelope

Every decrypted ELF except Fish Hunter SKL 2's is a Sentinel HASP envelope
(Fish Hunter has a plain `_start` and only calls the API through its
`THaspKeyPro` class):

- 8 MB of high-entropy body;
- the entry point (0x88b273a) in a stub at the end of the data segment;
- `/dev/Hardlock` and `/tmp/.aksusb` (built on the stack) in the stub.

The cabinet starts the HASP daemons before the game. The body's keys come
from the dongle. Running the game needs either the dongle's answers or the
unpacked memory image of the running game, as with Raw Thrills' dumps.
